# API Hook 实机问题排查与修复（2026-11-03）

## 诊断基线

沿用 Windows 10 19045 Hyper-V 虚拟机、专用 COM10↔20、COM11↔21、COM12↔22；不改变安全配置和驱动。时间以报告中的 UTC 为准。先运行仅添加诊断的版本，保留原有零等待锁策略和容量。

| 架构 | 业务完成 | 采集完成 | 丢弃增量 | 队列峰值 | 读取会话争锁累计 | 发布争锁累计 |
|---|---:|---:|---:|---:|---:|---:|
| x64 | 7440 | 6826 | 614 | 19/256 | 375 | 276 |
| x86 | 7444 | 7423 | 21 | 24/256 | 19 | 3 |

分类为本会话累计值，包含此前 1 秒预热；预热分别丢弃 37、1，故 651−37=614、22−1=21。两架构均满足完成记录加丢弃增量等于业务完成，字节错误为零。队列容量、跟踪容量和异步歧义均为零。与旧报告的架构高低相反，证据支持“消费者与生产者锁竞争受调度影响”，不支持“x86 天生更易丢失”或“队列太小”。

短测 Hook/无 Hook 吞吐比 x64 1.0331、x86 1.0275，p99 增量 119、152 μs。这是虚拟串口节奏测试，不代表物理线路吞吐。原生完整回归均通过；真实 .NET 单轮 x64 四条/28 字节通过，x86 三条/21 字节失败，正确性仍未验收。

原始报告在 [baseline](samples/process-hook/2026-11-03/baseline/)；历史 2026-10-28 失败样本不修改。

## 统计口径与复跑

诊断基线使用 ABI v3，记录体仍为 2464 字节，头部从 64 扩为 128 字节。最终实现为 ABI v4：头部 176、诊断区 104、记录体 2464 字节；每个异步计数保存 epoch/count 原子对，防止旧会话迟到完成或争锁失败污染新会话。旧驻留 DLL 必须重启目标。`NativeProcessMonitorTransport.Diagnostics` 提供累计快照，VmTests 按周期导出，附 QPC 频率。

- `SnapshotContention`、`PublishContention`、`CompletionContention` 分别统计会话快照、发布、完成会话校验的锁失败；`QueueFull`、`HandleCapacity`、`PendingCapacity` 为对应观察丢失；`AmbiguousCompletion` 为无法归属的观察丢失。静止后七项之和等于总丢失，运行中跨字段采样可能暂时不一致。
- `RetirementCapacity` 是跟踪退化警告，不是额外业务完成丢失。`NotificationLoss` 仅表示诊断通知未入队，原观察已计数，禁止再次增加总丢失。异步丢失是观察计数，不能直接当成业务完成数。
- `QueueHighWater` 是会话最高占用；`PublishCalls/PublishTicks/MaxPublishTicks` 统计取得队列锁后的发布调用及其包含锁尝试的处理时间。未取得锁的调用单独由争锁计数表示。只调用两次 QPC，无日志、堆分配或每字节计时。

构建使用 `Build-Hook.ps1` 或已生成的 Visual C++ `artifacts/{x64,x86}/build.cmd`；执行两个架构的 `HookContractTests.exe --diagnostics` 和无参数完整合约，再运行 `dotnet run --project tools/ProcessMonitor.HostTests -- src/FlexCom.ProcessHook/artifacts`，以及 `dotnet test tests/FlexComDotnet.Tests/FlexComDotnet.Tests.csproj`。

诊断合约分别复现三个锁失败点、消费者暂停/突发、八线程同步写入、句柄/挂起/完成地址容量耗尽、异步复用及诊断通知丢失。新增通知测试曾明确失败于重复计数，修复后必须通过。原生与 .NET 宿主合约验证新增诊断布局。

VmTests 包根目录存在 `diagnostic-baseline.txt` 时使用 30 秒采样；不存在时仍为 30 分钟。短测不得标为长期验收。

## 常规丢弃修复

消费者原来在队列锁内逐字节读取并分配记录，生产者则零等待取锁。改为预分配整环缓冲，在锁内最多两次批量复制，锁外解码和分发；生产者锁等待参数为 10 ms。队列仍为 256 条，句柄、挂起请求和完成地址仍各限制 1024 项，未放大容量或改用无限等待。调度延迟可能超过等待参数，不能声称业务 API 总耗时硬上限为 10 ms。

128 个线程同时完成的合约在原零等待策略下失败，2 ms 等待在 x86 仍失败，最终 10 ms 通过。消费者持锁、满队列和容量耗尽各自有独立断言，八线程 800 次突发测试仍要求完成加丢弃守恒。正常数据观察与诊断通知分开计数，通知不能再次增加总丢失。

## .NET 完成归属修复

实际根因已转为失败合约：原 API 立即成功返回之前，运行时可能已经取出完成包并复用 OVERLAPPED。此时观察者再次 GetOverlappedResult 得到新控制请求的四字节结果，将真实七字节写入错误记录为四字节。修复以覆盖到的完成包/业务完成查询为依据，使用请求 ID 防止地址复用，不用请求长度推断实际完成长度。

- 已观察到的事件式句柄、hEvent 低位抑制，以及提交前启用 skip-success 模式的立即完成，可在仍拥有 pending 归属时查询真实结果。通知模式在提交时快照，不能因另一线程稍后启用该模式就查询旧请求。挂起请求仍等待真实完成。
- WaitCommEvent 按地址识别复用，包括换句柄后复用；旧串口观察显示明确缺口，不读取控制结果作为串口数据。
- 读取载荷在 pending 归属锁内快照，随后移除请求、释放锁和发布，避免另一完成消费者先返回导致业务释放或复用读取缓冲区。
- 分类计数使用 64 位 epoch/count CAS，托管宿主在队列锁内原子换代；旧完成即使等待队列锁超时，也不能增加新会话丢失。回调仍调用一次。

测试先后证实旧实现会出现七字节变四字节、已消费后重复查询、跨句柄控制复用错配、旧会话争锁计入新会话、读缓冲区被另一消费者覆盖、通知模式晚变更误判。全部新增合约在修复后双架构通过。`--reuse` 为集中回归入口；无参数完整合约继续覆盖事件、单项/批量 IOCP、回调、错误码、取消、关闭、停止与跨会话。

模式依据：[SetFileCompletionNotificationModes](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setfilecompletionnotificationmodes) 规定立即成功可抑制完成包且已启用模式不能移除；[GetQueuedCompletionStatus](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-getqueuedcompletionstatus) 说明 hEvent 低位可阻止完成包入队。在途 I/O 期间并发改变通知模式的完整捕获仍未验收。

### 最终 v4 的真实 SerialPort

COM12↔22、.NET 10，单轮已知七字节载荷；压力每方向 200 轮并行，七字节内编码方向和轮次，逐组验证一发一收、句柄映射及唯一请求 ID。原始报告位于 [final-v4](samples/process-hook/2026-11-03/final-v4/)。

| 路径 | x64 | x86 | 结论 |
|---|---:|---:|---|
| 启动单轮 | 4/4 条，28 字节 | 4/4 条，28 字节 | 通过 |
| 启动并发复用 | 800/800 条，5600 字节 | 800/800 条，5600 字节 | 通过 |
| 附加单轮 | 3/4 条，21 字节 | 3/4 条，21 字节 | 失败 |
| 附加并发复用 | 798/800 条，5586 字节 | 797/800 条，5579 字节 | 失败 |

所有业务字节检查成功，失败的是采集完整性。附加前已进入的运行时完成等待可能绕过后来安装的 Hook，无法回溯；识别到 WaitCommEvent 复用时可给出已知缺口，但不能测出所有漏采数量。界面和每次附加的可导出“能力提示”明确这一限制，提示本身不增加已知丢弃。附加路径不能标为完整捕获。

中间 v3 同载荷压力样本仍保留于 [reuse-v3](samples/process-hook/2026-11-03/reuse-v3/)。该轮附加压力偶然 800/800 通过，不能覆盖单轮失败，也不能证明不同轮次/方向没有错配；最终改用不同载荷并保留更严格失败结果。
